SECTION 01

What we are actually building

✈ In airport terms: we are not building one airplane. We are building the entire airport — runways, tower, hangars, security, and the engineering bay that designs better planes every week.

NeuralScope is two things bolted together. The first is the Engine — a backend program that lives on your computer, takes objectives ("build me a landing page", "research this market", "fill in this Google Doc"), breaks them into steps, assigns AI models to each step, runs them, checks the results, and saves everything it learned. The second is the World — the 3D environment you already designed, which is a live window into the Engine. Every sphere, block, and line in the World corresponds to a real, running thing in the Engine. Click it, and you see its real state. Pause it, and the real process pauses.

The single most important design decision in this whole document is this: the 3D world never does any work itself. It is a screen, a beautiful one, into the Engine. The Engine does all the work and broadcasts everything it does as a stream of small messages ("worker booted", "step completed", "validation failed"). The World listens to that stream and draws it. This separation is what makes the system clean: you can rebuild the visuals a hundred times without touching the brain, and evolve the brain without breaking the visuals.

THE ONE-SENTENCE VERSION

A program on your machine runs teams of AI workers through checked, repeatable pipelines; everything it does is broadcast as events; the 3D world renders those events as living structures you can inspect and reshape.

SECTION 02

The airport metaphor — the full map

✈ Learn these twelve mappings and you understand the entire system. Every later section just zooms into one of them.

CONTROL TOWER → THE ORCHESTRATOR

One program that sees everything, schedules everything, and is the only authority allowed to start or stop flights. The Engine's core.

FLIGHT PLAN → THE TASK GRAPH

Before any plane flies, a route is filed. Before any work runs, the objective is compiled into a step-by-step graph: what happens, in what order, with what checks.

PILOTS → WORKER MODELS

The AI models (local or via API). Replaceable, specialized, never in charge of the airport. A pilot flies one plane; a worker runs one step.

PILOT TRAINING MANUALS → SKILLS

Markdown files of instructions and examples attached to a worker before takeoff. Same pilot + different manual = different capability.

THE BLACK BOX → TRANSPARENCY BLOCKS

Every flight records everything: every input, output, decision, and timing. Nothing is invisible. This recording is also the raw material evolution feeds on.

AIRPORT SECURITY → SECURITY CYCLES

Checks at every gate: is this worker doing what the flight plan says? Has it drifted? Should it be rebooted and re-grounded on the objective?

ENGINEERING BAY → EVOLVER BLOCKS

Engineers who read black-box recordings of failed or slow flights, redesign the plane, test the new design in the hangar, and only then roll it out to the fleet.

HANGAR → TESTING ENVIRONMENT

Where redesigned planes fly trial runs against the old design. Nothing touches passengers until it wins here.

CHARTER FLIGHT → ONE-TIME ENVIRONMENT

A flight that exists for one job: take off, deliver, land, scrap the plane. No learning is kept.

GATES → CONNECTORS

The doors between the airport and the outside world: Google Docs, your file system, web APIs, local LLM runtimes, payment tools. Each gate has its own security level.

CARGO WAREHOUSE → MEMORY

What the airport keeps between flights: facts, results, learned procedures. Important cargo gets a permanent warehouse slot; junk decays and is thrown out.

THE DEPARTURES BOARD → THE 3D WORLD

The live display. It shows reality; it never invents it. You, standing in the terminal, watching everything — and able to walk up and redirect a flight.

SECTION 03

The five layers of the system

✈ An airport is layered too: ground, runways, tower, airspace, and the world beyond the fence. Each layer only talks to the layer next to it.

The rule that keeps this clean forever: no layer skips a layer. The 3D world never calls Google Docs directly. A worker never draws anything on screen. The Tower never executes code itself — it asks the Runway layer to. When something breaks, you always know which layer to look at, because each layer has exactly one job.

The recommended stack (clean, boring, proven)

Engine: Python with FastAPI and asyncio — the AI ecosystem (model clients, vector stores, Google APIs) lives in Python, and async lets hundreds of light processes run on one machine. Event bus: in-process pub/sub written to a SQLite event log (upgradeable to Redis later — don't add infrastructure before you need it). State: SQLite for the registry (circuits, skills, connectors, versions) plus a local vector store (Chroma or LanceDB) for memory. Local models: Ollama, because it gives you a one-line install, a standard API, and hot model swapping. Heavy reasoning: a frontier API model (e.g. Claude via API) used sparingly as the planner/coordinator. Connectors: MCP (Model Context Protocol) servers wherever they exist — Google Drive, file system, browsers — so you inherit a standard instead of hand-writing every integration. Frontend: the three.js world, connected by one WebSocket.

SECTION 04

Every block, explained

✈ Each shape in the 3D world is one of these seven things. Here is exactly what each one is in the Engine — its job, its inputs, its outputs, and what happens when it fails.

1 · The Objective Node — where everything begins

You type or speak an objective in plain language. The Engine sends it to the Objective Compiler: a single call to the strongest model available, with one job — turn human intent into a machine-readable flight plan. The compiler outputs a JSON document containing: the goal restated precisely, success criteria (how we will know it's done), the list of steps as a graph (some steps depend on others; independent steps run in parallel), which worker profile each step needs, which skills to attach, which connectors each step is allowed to touch, and a risk rating that decides how much security wraps around it.

{
  "objective_id": "OBJ-2026-0613-001",
  "goal": "Build and deploy a one-page site for the bakery brand",
  "success_criteria": ["site loads locally", "all 4 sections present", "lighthouse > 85"],
  "risk": "medium",
  "environment": "one-time",
  "steps": [
    { "id": "S1", "task": "research 5 reference bakery sites", "worker": "researcher",
      "skills": ["web-research.md"], "connectors": ["web"], "depends_on": [] },
    { "id": "S2", "task": "write copy for 4 sections", "worker": "writer",
      "skills": ["brand-voice.md"], "connectors": [], "depends_on": ["S1"] },
    { "id": "S3", "task": "build HTML/CSS", "worker": "coder",
      "skills": ["frontend.md"], "connectors": ["filesystem:project/"], "depends_on": ["S2"] },
    { "id": "S4", "task": "validate against success criteria", "worker": "validator",
      "skills": ["qa.md"], "connectors": ["filesystem:project/"], "depends_on": ["S3"] }
  ]
}

This JSON is the circuit you see in 3D. Each step becomes a node. Each "depends_on" becomes a line. The shape of the structure in the world is literally the shape of the plan.

2 · Worker Models — the red spheres

A worker is not a model. A worker is a wrapper around a model: a small runtime that holds (a) which model to call — a 3B local model through Ollama, or an API model, hot-swappable, (b) the skill files injected into its context, (c) the tools/connectors it is permitted to use, (d) a step budget and timeout, and (e) a structured output format it must answer in. The Tower boots workers on demand: when step S3 becomes ready, the Tower spins up a "coder" worker, injects frontend.md, hands it S2's output as input, and tears it down when the step ends. Workers are disposable by design — intelligence lives in the structure around them, exactly as your vision states.

3 · Skills — the green slabs

A skill is a markdown file in a folder: /skills/web-research.md, /skills/frontend.md. It contains instructions, examples, checklists, and known failure patterns for one capability. Skills are what let a small model punch above its weight — instead of hoping a 3B model "knows" how to write good HTML, you hand it a battle-tested manual. Because skills are plain files, three things become true: you can edit them live (in the 3D world or any text editor — next worker boot picks up the new version), the Evolver can rewrite them (an improved skill is just a new version of the file, A/B tested in the hangar), and they are versioned in git, so every change is reversible.

4 · Code Structure — the blue rays

This is the most misunderstood part of agent systems, and the part your vision gets right. The blue rays are deterministic code — not AI — that scaffolds each worker: input parsers that clean what goes into the model, output validators that reject malformed answers before they propagate, retry loops with modified prompts, step decomposers that split a too-big task automatically, and checkpointing so a crashed step resumes instead of restarts. The honest framing: a small LLM is a brilliant but unreliable intern; the code structure is the standard operating procedure that makes the intern's work shippable. Most of the system's real quality comes from this layer, and it's also the layer the Evolver improves most often.

5 · Transparency Blocks — the turquoise frames

Every single action in the Engine emits an event: worker.booted, step.started, model.called (with the full prompt and response), validation.failed, step.completed. The Transparency layer does three jobs with that stream: it records everything to the event log (the black box), it summarizes in real time (so when you click a node, you see "currently: rewriting section 2 after validation failed on word count" instead of raw logs), and it analyzes — a small background worker reads recent traces and files structured reports: "the coder worker fails 30% of the time on CSS grid tasks", "step S2 outputs are drifting from brand voice". Those reports are the input feed to the Evolver Blocks. One honest note: we cannot literally read a neural network's internal thoughts; what we can capture is every prompt, every response, every intermediate reasoning step the worker writes down, every tool call, and every validation result — which in practice is a complete record of behavior.

6 · Security Cycles — the white spheres

Security runs at three rings. Ring 1 — per step: before any step executes, a gatekeeper check: is this connector in the step's allowed list? Is this file path inside the permitted folder? Is this shell command on the allow-list? Ring 2 — per worker: a drift monitor compares what the worker is producing against the step's stated task; if similarity drops or the worker loops, it's rebooted with a re-grounded prompt containing the original objective (your "regain focus, regain objective" cycle, literally implemented). Ring 3 — per environment: anything touching money, credentials, sending emails, or deleting files outside the project folder requires a human approval event — it shows up in the 3D world as a pulsing amber gate that waits for your click. Plus one global, physical control: the kill switch, a single command that freezes every worker and closes every connector instantly.

7 · Evolver Blocks — the green giants

Covered fully in Section 09, but the one-paragraph version: an Evolver is a scheduled pipeline that reads Transparency reports, picks the worst-performing structure (a skill, a prompt template, a validator, a step decomposition), generates 2–5 mutated alternatives, replays recorded real tasks against each alternative in the Testing environment, scores them against the originals, and promotes the winner — writing a new version of the file and logging the change. It is slow, heavy, and deliberate on purpose: it runs on cycles (e.g. nightly, or after every 50 completed objectives), not constantly.

The three environments, precisely

MAIN

What it is in code: the registry of promoted, versioned structures — skills, templates, pipelines marked stable — plus all long-running circuits (watchers, schedulers, recurring jobs). Only the Evolver's promotion step can write here. It accumulates; it never resets.

TESTING

What it is in code: a sandboxed copy of the runtime where candidate structures run against recorded replay tasks with scoring enabled and all external write-connectors mocked. Nothing here can touch your real files, docs, or accounts.

ONE-TIME

What it is in code: a job whose flight plan has persist: false. It runs in a temp folder, delivers its output to you, and its memory writes are discarded. The trace is kept briefly for the Evolver, then expires.

SECTION 05

How the system boots

✈ Opening the airport in the morning: power the tower, check the runways, unlock the gates, light the departures board.

Step 4 is what makes the world feel alive and permanent. The Engine doesn't start "empty" — it reloads every circuit that was live when it last shut down, from checkpoints, and resumes their schedules. Recurring circuits (a watcher that checks a Google Doc hourly, the nightly Evolver cycle, a memory-decay sweep) simply continue. When the 3D world connects, it receives one snapshot message describing every existing structure, draws the whole ecosystem, and then switches to live event mode. That's why opening NeuralScope feels like entering a place where things are already happening — because they are.

SECTION 06

The life of one objective — minute by minute

✈ One complete flight, from the moment you file the plan to wheels-down, including what you see in the world at every moment.

01

You define the objective

Typed in the world's command bar (or spoken, later). The world sends one command down the bridge: {"cmd":"objective.create","text":"...","env":"one-time"}. A faint seed-node appears immediately at the edge of the chosen territory.

02

The Compiler files the flight plan

The Tower calls the planner model with your text plus relevant memory. Out comes the task-graph JSON (Section 04). Risk is rated; required connectors are listed; if any connector needs a permission you haven't granted, the plan pauses at an amber gate. In the world: the seed-node sprouts — one node per step, lines per dependency. You are literally watching the plan being drawn.

03

The Scheduler finds ready steps

Any step whose dependencies are complete is "ready". The scheduler boots one worker per ready step, up to a concurrency limit. Independent steps run in parallel — this is one of the two honest ways the system beats human speed (the other is never sleeping).

04

A worker boots

The runtime assembles the worker: model selected (cheapest profile that historically passes this step type), skills injected, tools scoped, output schema attached, timeout armed. Event: worker.booted. In the world: a red sphere ignites on the step node, its skill slabs clicking into place, blue scaffold rays extending.

05

The step executes inside the scaffold

The deterministic loop: build prompt → call model → parse → validate. Validators are real code: does the JSON parse, do the files exist, does the HTML pass lint, do tests pass, does output match success criteria for this step. Pass → step output saved, checkpoint written. Fail → retry with the failure injected into the prompt (max N times) → still failing → security reboot with re-grounded objective → still failing → step marked failed, becomes a visible red fracture in the world, and a failure report is filed to the Evolver feed. The objective routes around it if the graph allows, or pauses for you if it doesn't.

06

Security watches the whole time

Ring-1 gate checks on every tool call; ring-2 drift checks every K seconds per worker; ring-3 human gates on anything irreversible. In the world: the white sphere orbiting the circuit pulses on every completed check cycle.

07

Final validation & delivery

The last step is always a validator worker checking the objective-level success criteria from step 02. Pass → outputs delivered (files in your output folder, doc updated, link presented) and the event objective.completed fires. In the world: the circuit settles, brightens once, and either takes residence (main) or gracefully dissolves (one-time).

08

The trace becomes fuel

The full black-box recording is summarized into memory (what worked, what failed, cost, duration) and queued as replay material for the next Evolver cycle. Every flight makes the next flight slightly better. That is the entire trick.

SECTION 07

Connectors — adding Google Docs, APIs, local LLMs, and code, live

✈ Gates can be opened, closed, and rebuilt while the airport is running. No shutdowns to add a new destination.

Every external thing the system can touch is a connector: a small standardized adapter with five parts — a manifest (name, what it does), credentials (stored encrypted, never inside prompts), a permission scope (read-only / read-write / requires-human-approval), the tool functions it exposes to workers, and a health check. All connectors live in a registry table, and the registry is hot: changes apply to the next worker boot, no restart ever needed.

Adding each type, concretely

Google Docs/Drive: you click "add gate" in the world → the Engine starts a one-time OAuth flow in your browser → you approve → tokens stored encrypted → the connector registers tools like docs.read, docs.append, docs.replace_section. From then on, any flight plan can request the gdocs connector, and a worker can complete entries in your documents. Removing it = one click, tokens deleted, gate vanishes from the world. Web APIs: add via a small manifest (base URL, auth header, allowed endpoints, rate limit) — the Engine auto-generates the tool functions and a mock for the Testing environment. Local LLMs: the Engine watches Ollama's model list; pull a new model with one command and it appears in the world as a new available energy source; model profiles (e.g. "coder = qwen2.5-coder:7b, temp 0.2, fallback → API") are registry rows you can edit live, and every worker boot reads the current profile. Code structures: validators, prompt templates, and step decomposers are versioned files in /structures/; editing one creates a new version marked experimental, which the Evolver (or you, manually) promotes to stable after it wins in Testing.

EDITING IN REAL TIME, EXACTLY

Everything editable is a file or a registry row, and nothing is loaded permanently into a running process — workers assemble themselves fresh at boot from the current state. So "editing in real time" means: you change a skill, profile, or structure → the change is versioned → every worker booted from that moment uses it → running workers finish on the old version (no mid-flight surprises). Clean, safe, instant.

SECTION 08

Memory — what the system keeps

✈ The cargo warehouse: important cargo gets a labeled permanent slot, routine cargo sits on shelves until unused, junk is swept out nightly.

Memory has three tiers, matching your "memory feels physical" rule. Tier 1 — Working memory: the live context of an active objective (step outputs, intermediate files). Lives only as long as the flight; in one-time jobs it's destroyed on landing. Tier 2 — Episodic memory: compressed summaries of completed objectives ("built bakery site; CSS grid failed twice; final cost $0.41; pattern: always validate fonts early"), stored as vectors so future planning can recall similar past work. Each entry has a relevance score that decays when unused — unused memories literally fade, and a nightly sweep deletes the faded ones. Tier 3 — Structural memory: the strongest form. When a pattern proves itself repeatedly, the Evolver graduates it from "a memory" into "a structure" — a new skill file, a new validator, a new pipeline template. Knowledge stops being something the system remembers and becomes something the system is. In the world: tier 2 appears as small crystalline nodes that visibly dim as they decay; tier 3 is permanent architecture.

SECTION 09

The Evolution Engine — how it actually gets better

✈ The engineering bay never touches a plane in flight. It studies the black boxes, builds a better wing, proves it in the hangar against real recorded flights, and only then refits the fleet.

Three rules make this safe and real instead of hand-wavy. Rule 1 — evolution targets structures, not models. We are not retraining neural networks (that's slow, expensive, and unstable on one machine). We evolve the things that demonstrably move quality: skills, prompts, validators, decomposition templates, model-routing profiles. This matches your vision exactly: the system grows smarter because the structures improve. Rule 2 — trials use recorded reality. Candidates are tested against replays of real past tasks with known good outcomes — never against made-up benchmarks. Rule 3 — promotion is gated and reversible. A candidate must beat the incumbent by a margin, across enough trials, with zero safety regressions; every promotion is a git commit; one click rolls back. In the world, you watch all of this: red threads feeding the green giant, clones competing in the hangar, and a green conduit pulse when a winner ships to Main.

SECTION 10

Security and the kill switch

✈ An airport with no security isn't fast — it's one incident away from being shut down forever. Same here, especially because this system touches your real files, docs, and eventually money.

"Complete access to my device" is the goal, but the engineering truth is that graded access is what makes complete access survivable. The system that can do anything, unsupervised, on day one is the system that deletes the wrong folder or emails the wrong person on day two. So permissions are tiered, and autonomy is earned per capability — exactly like the Evolver earns promotions:

TIER A · AUTONOMOUS

Read files in project folders, run sandboxed code, call read-only APIs, write inside designated workspaces. No approval needed. The system lives here 95% of the time.

TIER B · NOTIFY

Writing to your Google Docs, committing code, publishing to a staging site. Executes autonomously but fires a visible notification node in the world you can review and reverse.

TIER C · APPROVE FIRST

Sending emails as you, posting publicly, deploying to production, deleting outside workspaces. Pauses at an amber gate in the world until you click approve.

TIER D · HUMAN ONLY

Money movement, account creation, credentials, legal/identity actions. The system prepares everything and hands you the final button. This tier should stay human for a long time — it's also where laws and platform rules live.

A capability can graduate tiers (C → B) after a clean track record you define — e.g. 50 consecutive approved actions with zero reversals. That is how "eventually all I do is monitor" actually happens: not by removing the gates on day one, but by the system earning its way through them with receipts. And above all of it, the kill switch: one global command (a key combo and a big red node in the world) that freezes every worker, closes every connector, and snapshots state — resumable, but only by you.

SECTION 11

Linking the Engine to the 3D world

✈ The departures board protocol: every event in the airport becomes one line on the board, instantly.

The bridge is one WebSocket carrying small JSON events. Every Engine action has exactly one event, every event has exactly one visual meaning, and the world keeps a dictionary mapping event types to animations. This table is the contract between backend and frontend — once frozen, both sides can be built independently:

ENGINE EVENT                      → WHAT THE WORLD DRAWS
─────────────────────────────────────────────────────────────────────
objective.created                 → seed node materializes in territory
plan.compiled        (graph json) → circuit grows node-by-node from seed
worker.booted                     → red sphere ignites, skills slot in
step.progress        (summary)    → pulse travels the step's edge
validation.passed                 → edge flashes green, settles white
validation.failed    (reason)     → red fracture + report thread to Evolver
security.check                    → white sphere pulse on its orbit
security.gate.waiting (tier C/D)  → amber gate node, pulsing, clickable
worker.rebooted      (drift)      → sphere blinks out, re-ignites grounded
objective.completed               → circuit brightens; persists or dissolves
evolver.cycle.*      (6 phases)   → the green giant's capture→promote dance
memory.written / memory.decayed   → crystal node appears / dims out
connector.added / .down           → gate appears on the globe / turns red

Commands flow back down the same pipe: circuit.pause, skill.edit, memory.inject, experiment.promote, gate.approve, objective.create. The world is a remote control, never a brain. And the "globe" you asked for becomes meaningful here, not decorative: the globe is the boundary of the system — connectors sit on its surface as gates to the outside world, the three territories float inside it, and the security layer literally is the shell. Inside the globe: trusted, observed, controlled. On the shell: every doorway in and out.

SECTION 12

The honest physics — read this section twice

✈ A flight plan that ignores physics doesn't produce a faster plane. It produces a crash. Here is exactly what is buildable, and on what timeline.

WHAT ONE WEEK ACTUALLY BUYS

One week builds the complete vertical slice: the Engine with all seven block types working, real objectives executing end-to-end with real local + API models, Google Docs and filesystem connectors live, the event bridge streaming into the upgraded 3D world, and one real evolution cycle demonstrably improving one real skill. That is a genuinely extraordinary week. It does not buy a superhuman that autonomously builds SaaS companies — pretending otherwise would guarantee we build neither.

Three more truths that shape the design, so nothing here surprises us later. First: small local LLMs plus scaffolding get dramatically better — that's real and proven — but the planner/coordinator role needs a frontier API model for complex objectives for the foreseeable future. The architecture handles this gracefully: model routing is just a profile, so as local models improve, you flip rows in a registry, not rebuild the system. Second: full autonomy on real-world consequences (money, publishing, accounts) is gated by trust and rules, not by code — platforms require human account owners, payment processors have terms, and an autonomous mistake at Tier D is expensive. The earn-your-tier system in Section 10 is the realistic road to "I just monitor", and it genuinely gets there — gradually, with receipts. Third: "evolves forever" has a real engineering risk called regression — an "improvement" that wins the benchmark but breaks something unmeasured. That's why trials use recorded real tasks, why promotion requires margins, and why every change is one click from rollback. Slow, heavy, deliberate — your own words for the Evolver — is not a style choice; it's the safety mechanism.

WHY THE VISION STILL STANDS

Nothing above shrinks the end goal. A system that runs 24/7, parallelizes across dozens of workers, never forgets a lesson, improves its own procedures weekly with proof, and graduates itself into more autonomy is — over months, not days — exactly the digital workforce you described. The week-one slice is the seed of that organism, built so that every later phase is an upgrade, never a rewrite.

SECTION 13

The 7-day build plan

✈ Seven days, one runway poured per day, planes flying by mid-week.

DAY 1

Skeleton + event bus. Python Engine scaffold: registry (SQLite), event log, pub/sub, WebSocket server, the event contract from Section 11 frozen as a schema file. The world connects and renders raw events as placeholder shapes by evening.

DAY 2

The Tower. Objective Compiler (planner model → task-graph JSON), scheduler with dependency resolution and parallelism, checkpointing. First end-to-end "hello objective" runs with stub workers.

DAY 3

Real workers + scaffold. Ollama integration, API model client, model profiles, skill injection from /skills, validators, retry/reboot loop, sandboxed code execution. First real deliverable: the Engine builds a small website end-to-end.

DAY 4

Gates. Connector framework + three connectors: filesystem (scoped), Google Docs (OAuth), one web API. Permission tiers A–D, the amber approval gate, the kill switch. Engine completes an entry in a real Google Doc.

DAY 5

Transparency + memory. Full trace recording, live node summaries for the inspector, episodic memory with decay sweep, failure report generation. Click any node in the world → real state, real reasoning summary, real confidence.

DAY 6

The Evolver. Capture → decompose → mutate → trial-by-replay → score → promote, on one structure type (skills) first. Run it against Day 3–5 traces and ship one provable improvement. The full cycle animates in the world.

DAY 7

The World, upgraded. The pretty mode: the globe shell with connector gates, refined geometry (instanced crystalline nodes, flowing energy edges, bloom), the three territories inside the sphere, polish on inspector + reshape controls. Demo day: one objective filed by voice/text, watched live, evolved overnight.

Sequencing logic: the event contract on Day 1 is what lets the backend (Days 2–6) and the final visual upgrade (Day 7) proceed without blocking each other — and it's why your 3D world from the prototype keeps working unchanged the entire week.

SECTION 14

Road to the digital company

✈ After the airport opens: more routes, bigger fleet, and eventually — an airline that runs itself while you read the reports.

P1

Weeks 1–2 · The Working Organism

The 7-day slice, hardened. Recurring circuits (watchers, scheduled jobs). 10+ skills. Nightly evolution. You file objectives daily and it delivers: sites, code, research, doc work.

P2

Month 1–2 · The Department

Multi-objective concurrency, browser-automation connector, email drafting (Tier C), long-horizon projects spanning days with their own circuits. First capability graduations C→B. The system researches its own improvement ideas and files them as objectives for your approval.

P3

Month 3–4 · The Studio

End-to-end product builds: brand research → naming → site → content → launch checklist, with you approving Tier C/D moments. First revenue experiments — productizing the system's outputs (templates, sites, content services) with you as the human owner of accounts and payments.

P4

Month 5+ · The Company You Monitor

Most capabilities at Tier A/B with clean track records. Your day: review the morning report the system writes about itself, approve the handful of gated actions, set direction. The Evolver has rewritten most of its own skills several times over. This is the "superhuman team" — arrived at the only way it really can be: earned, audited, reversible.

SECTION 15

Glossary — every term in one place

Objective
A goal you give the system in plain language. The only way work ever starts.
Flight plan / Task graph
The compiled, machine-readable plan: steps, dependencies, workers, skills, permissions, success criteria.
Circuit
One objective's living structure — its steps, workers, and connections — as it exists in the Engine and appears in the world.
Worker
A disposable runtime wrapping one model call-loop for one step: model + skills + tools + validators + timeout.
Skill
A versioned markdown manual injected into a worker that specializes its behavior.
Code structure / Scaffold
Deterministic code around every worker: parsing, validation, retries, decomposition, checkpoints. Where most reliability comes from.
Transparency block
The recording + live-summarizing + analyzing layer. Source of all inspector data and all failure reports.
Security cycle
Recurring checks: tool gatekeeping, drift detection with re-grounding reboots, and tiered human gates.
Evolver block
The scheduled pipeline that mutates structures, trials them on recorded real tasks, and promotes proven winners.
Connector / Gate
A standardized, permissioned adapter to anything outside: Docs, APIs, models, files.
Event bus / Bridge
The stream of JSON events describing everything the Engine does; the world's only source of truth.
Main / Testing / One-Time
The promoted permanent registry + live circuits; the sandboxed trial ground; the ephemeral job space.
Kill switch
